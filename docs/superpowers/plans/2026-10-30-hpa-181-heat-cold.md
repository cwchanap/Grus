# HPA-181 — Heat and cold implementation plan

**Issue:** https://linear.app/cwchanap/issue/HPA-181/grus-survival-58-heat-and-cold-surface-efficiency

## Why this task and code survey

- Linear HPA-181 is now In Progress; its only blocker HPA-450 is Done and merged. HPA-181 unblocks HPA-188's research/tower milestone implementation. Art/SFX tickets stay separate.
- `catalog.rs` currently has seven `BuildingKind` variants and a `BuildingSpec` without heat fields. All costs, footprints and durations already use this catalogue. The one new Furnace fits the existing building path.
- `buildings.rs` handles validated placement, paid construction, builder handoff, completion, HP and ordinary destruction. No furnace-specific command is needed.
- `economy.rs::TeamEconomy` stores integer Coal in the shared Team-1 stockpile; `ResourceStockpile::try_spend` already enforces prices. Heat burning is the one new continuous-consumption path.
- `production.rs::step_production` tracks `progress_seconds` for the queue head, and `combat.rs::step_combat` ticks `AttackCooldown` globally before turret acquisition; modify only these rate multipliers. Turrets already use shared `strike`.
- `grus-godot/src/lib.rs::build_app` currently owns eight ordered gameplay wrappers between command application and feedback drain. `system_order.rs`, session tests and fixture tests **manually repeat different subsets**, so they cannot detect a runtime ordering regression. Consolidate complete ticks in `grus-sim::step_tick` and make the bridge and full-tick tests call it.
- `GrusBridge.economy_snapshot` already feeds the HUD, and `update_health_bars` pushes per-building state from Rust to views with `GodotNodeHandle`; reuse those patterns instead of a new bridge query and GDScript building polling. `main.tscn` has a 100px EconomyPanel, six-button BuildGrid with only 76px height, and TrainGrid starting at y=92. A seventh button requires a third build row and a deliberate layout change.
- `economy_smoke_test.gd` already tests the actual HUD and construction UI, while `reset_test.gd` covers restart; reuse them for a small heat boundary leg. **Important:** the economy smoke resets its fixture after the Bunkhouse/Depot leg and before the Barracks leg (`economy_smoke_test.gd:557`), so those structures are never all completed together. The suggested extra turret+furnace alone would not create a cold state; add one more heat-demanding building in the Barracks leg, plus real resource gathering as needed. CI already covers sim, headless smokes, export/E2E and benchmark.

## Checkpoints on the same PR

The following are implementation stages **inside this single PR**, not separately tracked tickets or follow-up PRs. Keep the branch mergeable between stages where practical.

### 1. Catalogue, seed and heat computation

**Files:** `crates/grus-sim/src/{catalog.rs,heat.rs,lib.rs,fixture.rs,buildings.rs}` and focused catalogue/heat tests.

- Append `CoalFurnace` to `BuildingKind`/`ALL` and existing `building_spec`: **2×2, 80 Scrap, 20 s, 300 HP**. Add catalogue `heat_supply`/`heat_demand` fields to every building kind, and named `FURNACE_COAL_PER_SECOND = 0.5` and `MIN_SURFACE_EFFICIENCY = 0.25` (names can follow existing style). Extend the current Team-1-only `Locked` validation in `buildings.rs`, not a new permission layer.
- Implement `HeatState { supply, demand, burn_remainder }` as one defaultable resource; derive `efficiency()` from supply/demand with zero-demand=1 and clamp floor 0.25. Provide `surface_efficiency(&World)` returning 1.0 when `HeatState` is absent, matching the existing optional-session convention. An inserted but not-yet-stepped default resource must also read 1.0.
- `step_heat(&mut World, seconds)` counts completed Team-1 buildings and recomputes supply/demand in **every** session phase. Furnace output is enabled by positive Coal at the start of the tick; only while Playing does it add `active_furnaces * 0.5 * seconds` to one pooled remainder and debit whole units from the shared Team-1 Coal stockpile. Cap depletion, clear the remainder when empty, and stop furnace supply next tick. Insert `HeatState::default()` beside `WaveState::default()` in `seed_skirmish`; reset re-inserts it. No separate initial refresh path or stored efficiency.
- Tests: 15/10 after the first Start-phase heat tick (without Coal burn), missing/default resource neutral value, complete vs site demand, demand-zero fallback, efficiency floor, 20Hz 0.5 Coal/s consumption with multiple furnaces, depletion/next-tick supply drop, refuel, non-Playing snapshot recompute without burn, destroyed buildings and restart remainder. Use deterministic time, not sleeps.

### 2. Canonical fixed-step integration and controlled rates

**Files:** `crates/grus-sim/src/{lib.rs,tick.rs,production.rs,combat.rs}`, `crates/grus-godot/src/lib.rs`, `crates/grus-sim/tests/system_order.rs`, full-tick helpers in `session/tests.rs` and `fixture/tests.rs`, and `CLAUDE.md`.

- Introduce a small `pub fn step_tick(world: &mut World, map: &mut GridMap, seconds: f32)` in `grus-sim`, executing **`step_waves → step_heat → step_combat → step_movement → step_economy → step_construction → step_production → refresh_visibility`**. This becomes the **single source of runtime tick order**. Delete the now-redundant separate `advance_waves/combat/movement/economy/construction/production/visibility` bridge wrappers; one `advance_sim` reads `Time<Fixed>` and runs `step_tick` inside the existing scoped GridMap borrow. Keep command apply before it and feedback drain after it.
- Convert `system_order.rs` and full-tick helpers in session/fixture tests to call `step_tick`; intentionally partial-step tests may retain explicit calls. Test the **actual** canonical tick to prove heat computed before combat and production, movement before construction/economy, and construction before production; tests must fail if `step_tick` is reordered. **Update `CLAUDE.md` in this same implementation PR**, including the actual new bridge chain and correction to the former misleading order-test statement.
- Apply `seconds * surface_efficiency(world)` at the existing **single** FIFO queue-head progress increment (all `ProductionQueue` producers already are completed Research Centers/Barracks; no kind filter). Maintain blocked-at-100%, spawn and population behavior.
- Split `AttackCooldown` decrement only by unit vs completed building/turret attacker; unit attackers keep `seconds`. `strike` keeps nominal cooldown and damage. Heat has no effect on Worker gather or construction speed.
- Tests: use the canonical `step_tick` for same-tick ordering regression, direct Rust tests for 100% vs cold rate, warm↔cold cooldown recovery, unchanged unit/gather/construction timing, and missing `HeatState` (no panic, full rate for production and combat). No second tower attack engine.

## Risks and mitigation

- **Tick-order drift:** manually copied step lists hide regressions. Make `step_tick` the sole full-tick sequence and have integration tests call the same function; keep partial sequences only when the test explicitly relies on a mid-tick state.
- **Smoke timing and solvency:** the economy smoke resets between build legs and real gathering needs time; a test that assumes a combined city or uses unfunded input will time out. Budget the second leg independently, use the actual 15/16 cold state, and isolate the boundary leg on reset if it approaches a live wave.
- **View synchronization:** cold state might arrive before the view has its team metadata. Cache the requested flag and apply it when normal team styling initializes; verify both late-attach and recovery without per-building HUD calls.
